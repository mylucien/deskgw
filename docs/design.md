# OpenWrt Web 远程桌面网关 · 软件设计方案

版本：v1.0　｜　目标平台：OpenWrt 22.03+（x86\_64 / aarch64 / armv7 / mipsel）

## 1. 项目目标与范围

**目标**：在 OpenWrt 路由器上运行一个轻量网关服务。用户通过浏览器访问路由器，登录后选择局域网内的 Windows 主机，输入该主机的 Windows 账号密码，即可使用 **Windows 原生远程桌面（RDP）** 进行操作，并可上传/下载文件。

**功能需求**

- Web 账号密码登录，支持**多个 Web 账号**，区分管理员/普通用户。
- 支持**多台 Windows 主机**，每台主机可由不同用户同时连接。
- 连接时再输入主机的 RDP 账号密码（默认不落盘）。
- 后台管理：增删改主机、管理 Web 用户、分配主机权限、查看在线会话/审计日志。
- 文件上传、下载（浏览目录、拖拽上传、多文件下载）。
- 剪贴板同步、全屏、分辨率自适应、键盘/鼠标完整支持。

**性能连接模式（新增）**：除 RDP 模式外，提供面向高帧率场景的性能模式。Windows 端安装 Airhand 被控端，用 GPU 硬编码传输画面（最高 120fps），可操作锁屏与 UAC，文件传输沿用 SMB 文件面板。用户界面不出现控制码和配对码，详见 4.8。

**非功能需求**

- 资源占用小：常驻内存 ≤ 40MB（不含会话），单会话增量 ≤ 10MB（网关侧）。
- 单个二进制 + 静态前端，通过 opkg 安装，procd 托管。
- 安全：全程 HTTPS/WSS，路由器不保存主机密码，所有操作可审计。

**不在范围内**：公网穿透、非 Windows 主机（VNC/SSH）、会话录屏、RDP 模式下的剪贴板文件互传（均列入后续规划）。

## 2. 技术选型与方案对比

路由器的 CPU、内存、Flash 都有限，核心问题是：**RDP 协议的解码由谁来做**。

| 维度 | 方案 A：Guacamole（guacd） | 方案 B：浏览器端解码（IronRDP WASM + TCP 隧道） |
| --- | --- | --- |
| RDP 解码位置 | 路由器（guacd + FreeRDP） | 用户浏览器（WebAssembly） |
| 路由器负担 | 重：CPU 编解码、依赖 cairo/pango/freerdp 等大量库 | 极轻：只做 WebSocket↔TCP 字节转发 |
| 安装体积 | 数十 MB，OpenWrt 无官方包，需自行交叉编译 | Go 单文件约 8–12MB（UPX 后更小） |
| 文件传输 | 原生支持（RDP 磁盘重定向） | 需另建通道（本方案用 SMB） |
| NLA/CredSSP | 成熟 | IronRDP 已支持，需实测兼容性 |
| 成熟度 | 高 | 中，需要关注上游版本 |
| 适用设备 | x86 软路由、≥1GB 内存 | 绝大多数 OpenWrt 设备（≥128MB 内存） |

**结论**：默认采用**方案 B**，因为它让路由器真正只做"中转"，且凭据只在浏览器与 Windows 之间完成 NLA 握手，路由器无法看到明文密码。若目标设备是 x86 软路由且追求最大兼容与原生磁盘重定向，可将"RDP 中继模块"替换为方案 A，其余模块（认证、用户、主机、审计、前端框架）完全复用。下文以方案 B 展开。

**性能模式的位置**：RDP 会话里难以使用 GPU 抓屏做高帧率传输，所以需要高帧率时另设性能模式（4.8）；RDP 模式和方案 B 保持不变。

**具体技术栈**

- 后端：Go 1.22+（静态编译，交叉编译方便），HTTP 框架 chi，WebSocket 用 nhooyr/websocket，数据库 SQLite（纯 Go 驱动 modernc.org/sqlite，免 CGO）。
- 文件传输：go-smb2（SMB2/3 客户端）。
- 前端：Vue 3 + Vite，RDP 画面使用 IronRDP Web（WASM），Canvas 渲染。前端构建产物嵌入 Go 二进制（embed）。
- 密码哈希：argon2id；会话：服务端 Session + HttpOnly Cookie。

## 3. 总体架构

```
┌────────────── 浏览器 ──────────────┐
│ Vue 前端：登录 / 主机列表 / 后台管理  │
│ IronRDP-WASM：RDP 编解码 + NLA      │
│ 文件管理面板（上传/下载）            │
└───────┬─────────────────────┬──────┘
        │ HTTPS REST          │ WSS（二进制流）
┌───────▼─────────────────────▼──────────────────┐
│               OpenWrt：deskgw 守护进程            │
│ ┌────────┐ ┌────────┐ ┌─────────┐ ┌──────────┐ │
│ │认证/会话│ │用户/主机│ │ RDP隧道 │ │ 文件网关  │ │
│ │ 模块    │ │ 管理    │ │ WS↔TCP  │ │ SMB 客户端│ │
│ └────────┘ └────────┘ └────┬────┘ └────┬─────┘ │
│ ┌────────┐ ┌────────┐      │           │       │
│ │ 审计日志│ │ SQLite │      │           │       │
│ └────────┘ └────────┘      │           │       │
└────────────────────────────┼───────────┼───────┘
                  TCP 3389   │           │ TCP 445
                     ┌───────▼───────────▼──────┐
                     │  局域网 Windows 主机 1…N   │
                     └──────────────────────────┘
```

**核心原则**：路由器只转发 RDP 字节流，不解析内容；主机地址由服务端数据库决定，浏览器永远不能指定目标 IP。

**例外**：性能模式下路由器只做握手并转发密文，画面在浏览器里解密，路由器不解析视频；但它持有握手用的长期密钥，并在握手后把会话密钥交给浏览器。组件与流程见 4.8。

## 4. 模块设计

### 4.1 认证与会话模块

- 登录：`POST /api/login`（用户名 + 密码）→ 校验 argon2id 哈希 → 下发 Session Cookie（HttpOnly、Secure、SameSite=Strict，默认 8 小时空闲过期；前端每 4 分钟打一次 `/api/me` 续期，切回前台补一次）。
- 防暴力破解：按「IP+用户名」计数，15 分钟窗口内连续失败 5 次锁定 10 分钟；同一 IP 跨用户名另有 50 次的总闸门。成功登录会清掉该键与来源 IP 的计数，避免偶发输错累积成锁定。
- 首次启动：无用户时生成 `admin` 与随机密码写入 `/etc/deskgw/initial-password.txt`（0600），日志只提示文件位置，不做初始化向导。登录后可用顶栏「改密码」自助修改（校验旧密码，保留当前会话，其余会话失效）。
- 可选增强：TOTP 双因素——当前只保留了 `users.totp_secret` 字段与只读的 `has_totp` 标记，功能未实现。
- CSRF：除 SameSite 外，写接口要求自定义头 `X-CSRF-Token`（登录接口也校验双提交 Cookie）。

### 4.2 用户与权限模块

- 角色：`admin`（全部权限）、`user`（仅能连接被授权的主机）。
- 授权模型：用户 ↔ 主机 多对多，支持"用户组 ↔ 主机组"后续扩展。
- 每个用户可配置：是否允许文件传输、是否允许剪贴板、最大并发会话数。

### 4.3 主机管理模块（后台）

- 字段：名称、IP/主机名、RDP 端口（默认 3389）、SMB 端口（默认 445）、备注、分组、连接方式、是否启用。
- 已实现：增删改查、用户授权、主机 id 显式递增（删掉最大 id 后不复用，避免与性能模式的注册表错位）。
- 未实现（后续）：TCP 3389 探活与在线/离线标记、批量导入 CSV、ARP/ICMP 局域网扫描辅助添加、定时巡检。
- 主机的 Windows 账号密码**不在后台保存**；"加密保存凭据"（AES-GCM，密钥由管理员口令派生）未实现，当前也没有计划。

### 4.4 RDP 隧道模块（核心）

连接流程：

1. 用户在主机列表点击"连接"，前端调用 `POST /api/sessions {host_id}`。
2. 服务端校验登录态与授权，创建会话记录，返回**一次性票据 ticket**（有效期 30 秒、仅可使用一次）。
3. 前端弹出对话框，用户输入 Windows 用户名/密码（可选域）。
4. 前端打开 `wss://router/ws/rdp?ticket=xxx`。服务端验证并销毁票据，从数据库取出主机 IP:端口，建立 TCP 连接到 Windows，开始双向转发二进制帧。
5. 浏览器内的 IronRDP 通过该隧道完成 X.224 → TLS → CredSSP(NLA) → RDP 会话；账号密码仅在浏览器与 Windows 之间被使用。
6. 任一端断开则清理连接并写审计日志。

实现要点：

- 使用 `io.Copy` 级别的零拷贝风格转发，每个会话 2 个 goroutine；WebSocket 帧设置读写缓冲与背压。
- 心跳（ping/pong 30 秒）与空闲超时（可配置，默认 30 分钟无数据断开）。
- 目标地址白名单：只允许数据库中已登记主机，且必须是私网地址段，防止 SSRF。
- 同一主机多人同时连接取决于 Windows 版本（家庭版/专业版仅允许单会话，服务端给出明确提示）。

### 4.5 文件传输模块

RDP 磁盘重定向在浏览器 WASM 中支持有限，因此采用**独立的 SMB 文件通道**，使用户在连接时输入的同一份 Windows 凭据访问目标主机。

- 前端"文件"面板：单层面包屑导航（不带树）、列表（目录优先、按名称排序）、上传（拖拽 / 选择文件，分片可续传）、下载（单文件流式、支持 Range）、新建文件夹、重命名、删除。多文件打包 zip 未实现。
- 接口：
  - `GET /api/files/list?session=…&share=…&path=…`
  - `POST /api/files/upload/{begin,chunk,finish,abort}`（分片；`begin` 声明总大小，`finish` 校验偏移，409 返回已收偏移供续传；覆盖已有文件需显式确认）
  - `GET /api/files/download?session=…&path=…`（流式、支持 Range）
  - `POST /api/files/mkdir|rename|delete`
- 服务端用 go-smb2 连接 `\\host\共享名`（默认可访问 `C$` 管理共享，也可切换共享名），**流式读写**，不在路由器落盘，避免耗尽 Flash/内存。写入是"临时文件 → 备份旧文件 → 改名覆盖 → 删备份"，失败可回滚。
- 凭据处理：文件会话使用独立的短期 `file_token`（绑定会话与来源 IP，30 分钟），凭据只保存在该会话的内存中，会话结束立即清除；令牌过期返回 403、会话结束返回 410，前端就地重取，不会把用户踢回登录页。
- 限制：单文件大小上限（默认 2 GiB，后台可调）、上传分片大小、全局 24 条 SMB 连接、单次读写 60 秒空闲上限；可禁止特定用户使用文件功能。每次文件操作都重新校验用户-主机授权。
- 前提：Windows 需开启文件和打印机共享，防火墙放行 445（文档中给出一键配置脚本）。

### 4.6 审计日志模块

记录：登录成功/失败、会话开始/结束（用户、主机、来源 IP、时长）、文件操作（上传/下载/删除的路径与大小）、后台配置变更、性能模式批准与下线。日志存入 SQLite，支持按时间/用户/动作检索与 CSV 导出；检索支持分页，关键词里的 `%`、`_` 会被转义，导出走 `limit=0` 取全量，不再有 20 万行截断。审计保留 90 天、每 24 小时清理一次；`sessions` 表按同样口径保留 90 天，避免只增不减拖慢列表与配额查询。

### 4.7 前端设计

页面：

- **登录页**；**主机列表页**（卡片 + 分组 + 搜索 + 刷新）；
- **会话页**：顶部工具栏（会话菜单、Ctrl+Alt+Del、全屏、剪贴板、文件面板、断开），支持多标签同时打开多台主机，标签数上限由服务端配额决定；离开页面时用 keep-alive 保活，会话不中断。
- **后台管理**：主机管理、用户管理、授权分配、在线会话（可强制踢下线）、审计日志、系统设置。

前端不缓存任何 Windows 密码；输入框使用 `autocomplete=off`，提交后立即清空变量。

### 4.8 性能连接模式（浏览器端解密）

> 实现状态：本节的 M7–M10 已落地，`internal/perfgw/` 与浏览器控制端可用，协议细节以 [`perf-protocol.md`](perf-protocol.md) 为准；下文提到的「M7 实测/确认」保留为当时的设计依据，实测结论已经写回该文档。没有开放的能力（多显示器、剪贴板图片等）仍按「不做」处理。

性能模式是 RDP 模式之外的第二种连接方式：Windows 端运行 Airhand 被控端（开源，MIT 许可，Rust），用 GPU 硬编码传输画面，目标是高帧率。OpenWrt 上**不部署 Airhand 的中继和网页控制台**，deskgw 内置的 perfgw 只做三件事：接受被控端接入、与被控端完成握手、把密文转发给浏览器。**画面和输入的加解密全部在浏览器里完成**，目的是尽可能减轻路由器负担。原则是只做满足需求的功能，其余一律不做。

**范围**

- 做：高帧率画面（被控端 GPU 硬编码，浏览器 WebCodecs 解码）；键盘、鼠标、滚轮输入；文本剪贴板双向同步；画质与帧率设置、请求关键帧、浏览器窗口尺寸；远程光标显示；锁屏与 UAC 画面；多主机、多账号授权（沿用 4.1–4.3）；文件传输沿用 SMB 文件面板（4.5）。
- 不做：Airhand 的中继、控制码、撮合；声音、麦克风；剪贴板的图片与文件（文本已做）；Airhand 自带的文件传输；直连打洞与多路径合并；多显示器切换（先固定主显示器，列入后续）；重连凭证、"我的设备"。

**与 RDP 模式的差异**

| 项目 | RDP 模式 | 性能模式 |
| --- | --- | --- |
| Windows 端 | 系统自带，无需安装 | 安装 Airhand 被控端（SYSTEM 服务） |
| 画面编码 | RDP 协议，浏览器 WASM 解码 | GPU 抓屏 + 硬件编码，最高 120fps，浏览器硬解 |
| 解密位置 | 浏览器与 Windows 间 NLA/TLS | 浏览器（WebCrypto） |
| Windows 登录校验 | NLA，连接时输入账号密码 | 在远程画面的锁屏界面输入，网关授权是外层防线 |
| 锁屏 / UAC | 受 RDP 会话限制 | 可看到并操作 |
| 文件传输 | SMB 文件面板（4.5） | 同一个 SMB 文件面板，用户另输 Windows 凭据 |
| 路由器负担 | 只转发字节 | 只转发密文：QUIC 解密一次、WSS 加密一次，不解析视频 |
| 同一主机多人 | 取决于 Windows 版本 | 同屏共享，默认每台主机限 1 个会话 |

> **锁屏与 UAC 的前提**：这两块界面在 Windows 的安全桌面（`Winlogon`）上，只有以 SYSTEM
> 身份运行的系统服务才打得开。被控端必须按「为所有用户安装」装成服务；「仅为我安装」/
> 便携版跑在登录用户的会话里，采集线程切不过去，UAC 期间控制端看到的是黑屏（关掉 UAC
> 后自动恢复），锁屏与登录界面同样看不到。换安装方式要**先卸载**，再以管理员身份运行
> 安装程序选「为所有用户安装」，装好后 `sc query Airhand` 能看到服务。详见
> [`perf-protocol.md` 的已知限制](perf-protocol.md#已知限制)。

**架构与分工**

```
浏览器：界面（fork 的 Airhand 控制台） + 浏览器控制端（Web Worker：解密、帧与消息处理）
   │ HTTPS / WSS（登录态 + 一次性票据）：握手结果、密文转发
deskgw（Go，单进程）
 ├─ 既有模块：认证 · 授权 · 主机表 · 审计
 └─ perfgw：QUIC 服务端 UDP 4433 · 握手 · 密文转发 · 背压
   │ QUIC / UDP 4433（局域网，被控端主动连入）
Windows 主机：Airhand 被控端（SYSTEM 服务，开机未登录即可连）
```

|  | 路由器（perfgw） | 浏览器（控制端） |
| --- | --- | --- |
| 握手 | 用路由器上的长期密钥完成 Noise 握手，派生各通道密钥 | 不参与，只接收会话密钥 |
| 加解密 | 不做 | AES-256-GCM（WebCrypto，硬件加速） |
| 帧与消息 | 不解析，原样转发（只给每个数据块加一个转发头） | 解析帧流、CBOR 消息，处理确认与丢帧恢复 |
| 长期密钥 | 保存，不下发 | 只持有当前会话的密钥，会话结束作废 |

没有 airhand-server、airhand-web，也没有额外的进程和 Docker。

**主机接入与批准**

- 被控端的 `server` 指向 deskgw 的局域网地址和 4433 端口，`server_fp` 填 deskgw 证书的指纹（后台"性能模式"页显示，构建安装包时写入）。
- 新被控端第一次连上来，deskgw 完成注册应答，并把它放进"待批准"列表（名称、系统、来源 IP、时间）。批准之前任何用户都不能使用它。
- 管理员批准只做准入：选择已有主机或新建，路由器把待批准的控制码换成主机 id，断开让被控端重连取新码。控制端公钥要等用户第一次真正连接、走完 Noise XX 才学得到（被控端在 `Confirm` 之前不显示控制端，安全码核对在实机上做不到），学到之后记进 `hosts.perf_key`，之后只用 Noise IK，公钥变化即阻断并要求重新批准。
- 批准结果与重连密钥同时落库（`hosts.perf_secret`）。网关重启后被控端带着控制码回来，路由器凭这对值直接认回「已批准」，不用管理员再批一次。
- deskgw 把"主机 id"作为控制码回给被控端，同时给一个 16 字节随机重连密钥，被控端重连时凭这对值识别身份（落库为 `hosts.perf_secret`）。
- 局域网里任何设备都可以冒充被控端来注册，所以未批准的连接不转发任何用户数据；注册接口限流，只监听局域网接口。
- 被控端放行控制端靠"配对过的公钥"。路由器持有一把固定的 X25519 控制端密钥，需要预先写入每台被控端 `config.toml` 的 `[[paired]]`，该方式未经验证，列入 M7；不可行则第二期实现 SPAKE2 配对。

**连接流程**

1. 用户登录后，主机列表按 `modes` 字段显示可用的连接方式。
2. 点击"性能模式"：前端调用 `POST /api/perf/ticket` 取 30 秒有效的一次性票据，打开 `wss://路由器/ws/perf?ticket=…`。
3. 浏览器在这条 WebSocket 上发 `connect`（主机占位符 `h<主机id>`、初始画质设置、窗口尺寸）；perfgw 校验用户对该主机的授权、会话名额，并确认该主机的被控端在线。
4. perfgw 分配会话号，在被控端的信令流上发 `Incoming`（带握手第一条消息），在控制通道上完成握手，并发出第一帧加密的 `Confirm`。
5. 握手成功后，perfgw 把这个会话的各通道密钥和计数状态通过 WSS 交给浏览器（`ready` 消息）。
6. 之后 perfgw 只做密文转发：被控端的流和数据报转给浏览器，浏览器发出的密文帧和数据报转给被控端。浏览器控制端解密画面后交给 WebCodecs 播放，输入、确认和设置在浏览器里加密后发出。
7. 主机保持锁定时，用户在远程画面里输入 Windows 账号密码登录。
8. 断开时写入审计日志（用户、主机、来源 IP、时长）。

**文件传输**

沿用 4.5 的 SMB 文件面板。性能模式下用户在面板里输入该主机的 Windows 凭据，规则与 RDP 模式一致：只存在于内存，会话结束即清除。Airhand 自带的文件传输依赖被控端的文件通道协议，属于"其他功能"，不做。

### 4.9 与 Airhand 被控端的对接接口

被控端用 Airhand 官方 Windows 客户端，不改一行代码；我们按它的协议实现服务端接入、握手，并让浏览器完成其余部分。以下细节读自源码 v0.3.1 的 `crates/airhand-proto` 与 `crates/airhand-link`，被控端升级前须重新核对。

**接入层**

QUIC 服务端，ALPN 为 `airhand/1`，使用自签证书（被控端用 `server_fp` 固定其指纹），开启 QUIC 数据报。信令版本号 10，要求与被控端精确一致。

**信令（被控端一侧只有四条）**

| 方向 | 消息 | 处理 |
| --- | --- | --- |
| 被控端 → deskgw | `ClientHello`（版本、角色、名称、系统） | 校验版本，回复 `ServerHello`，文件上限填空 |
| 被控端 → deskgw | `Register`（重连凭证、keep、rekey） | 回复 `Registered`（控制码 = 主机 id，重连密钥）；无凭证的进入待批准 |
| deskgw → 被控端 | `Incoming`（会话号、对端信息、地址、握手第一条消息） | 有用户连接时发送 |
| 被控端 → deskgw | `Release`、`Rekey` | 被控端本机用户更换控制码时发来，回最简应答并要求管理员重新批准 |

`Connect`、`ConnectResult`、`HostOnline` 是控制端与中继之间的消息，我们不需要。消息是带编号字段的 CBOR。

**会话传输格式（中继与直连同一格式，我们直接在被控端这条连接上收发）**

- 单向流开头 9 字节：`会话号 u64 小端 | 通道号 u8`。通道 0 是控制，1 是大块，2–5 是视频（每帧一条流），6 是文件（不用）。控制和大块是常驻流。流内按长度前缀分帧，前缀格式以 `framing.rs` 为准（M7 确认）。
- 数据报：`会话号 u64 小端 | 种类 u8 | 密封单元`，种类 0 是声音（不用），1 是控制数据报。单个数据报上限 1000 字节。
- 握手之后每一帧、每个数据报都是密封单元；握手最后一步，控制端在控制通道上发出第一帧加密的 `Confirm`，被控端解开后才显示控制端。

**握手（在路由器上完成）**

- 首次用 `Noise_XX_25519_ChaChaPoly_BLAKE2s`，已记录被控端公钥后用 `Noise_IK_25519_ChaChaPoly_BLAKE2s`。控制端第一条消息放在 `Incoming.init`，后面几条在控制通道上以明文 CBOR 交换；被控端的决定在最后一条回复里，用控制通道的会话密钥加密。
- Noise 的 prologue 绑定握手请求；会话版本为 1，要求精确匹配。
- 握手结束得到两样东西：32 字节的握手哈希 `h`，以及两把原始密钥（控制端到被控端、被控端到控制端）。被控端用的是 `snow` 的 `risky-raw-split`，Go 侧如果 Noise 库不暴露原始密钥，就自己实现 Split（基于 BLAKE2s 的 HKDF，几十行）。
- 带配对码的 XXpsk3 与 SPAKE2 在第二期，仅当预置配对不可行时才做。

**会话密钥与加密格式（决定了浏览器能不能解）**

- 每个通道、每个方向的密钥：`HKDF-SHA256(salt = h, ikm = 对应方向的原始密钥, info = 通道标签)`，输出 32 字节，用于 AES-256-GCM。标签字符串以 `secure.rs` 为准。
- 密封单元：`密文 | 16 字节标签 | 8 字节计数（小端）`；nonce 为 12 字节，前 4 字节为 0，后 8 字节是计数（小端）；不带附加数据。
- WebCrypto 的 AES-GCM 输入是"密文接标签"，去掉末尾 8 字节计数后正好符合，所以浏览器可以直接解，并使用硬件加速。
- 接收规则：控制通道和大块通道必须按计数顺序；视频和数据报用滑动窗口防重放，允许乱序。
- 握手完成时，控制通道两个方向的计数都已用掉第一个（`Confirm` 与被控端的决定），起点以 `secure.rs` 为准，M7 确认。

**路由器交给浏览器的会话密钥包**

控制通道（收、发各一把，带计数起点）、控制数据报（收、发各一把）、视频通道 0–3 的接收密钥。视频只收不发，大块通道只由路由器读取并丢弃，不下发。

**最小消息集（由浏览器解析和发送）**

| 方向 | 消息 | 做法 |
| --- | --- | --- |
| 被控端 → 浏览器（控制通道） | `Hello`、`Displays`、`Encoder` | 必须解析，用于画面尺寸与编码信息 |
|  | `Cursor`、`CursorImage` | 交给界面显示光标 |
|  | `Notice` | 转成提示 |
|  | `Bye` | 结束会话 |
|  | `Clipboard`、`Mic`、`Files`、`Direct` | 解析后丢弃；直连候选不回应，会话继续走这条连接 |
| 浏览器 → 被控端 | `Input`、`Settings`、`RequestKeyframe`、`View` | 必须；`Settings` 先发默认值，再响应界面的设置 |
|  | `SelectDisplay`、`Clipboard`、`Audio`、`Mic`、`Direct`、`Files` | 不发 |
| 数据报 | `Ping` ↔ `Pong` | 周期心跳，用于失联检测 |
|  | `Ack` | 每完成一帧确认，驱动被控端流控 |
|  | `Lost` | 丢帧通知，换关键帧恢复 |
|  | `Report`（视频质量反馈） | 已实现：每 500ms 报本周期帧数/卡住帧数，用于码率自适应 |
|  | `Echo`、`Probe` | 直连专用，不做 |

`CursorImage`（光标形状）走大块通道，浏览器按槽位/代际缓存后自绘；`Lost` 暂不做，
缺帧仍用 `RequestKeyframe` 兜底。上表"必须"与"建议"是对消息作用的判断。

**视频**

每帧一条单向流，流内是一组密封的媒体包。路由器原样转发给浏览器，浏览器控制端用 WebCrypto 解密，组帧后交给 WebCodecs 解码；每完成一帧，浏览器发出一个 `Ack` 数据报。

**已验证（2026-11-26，Airhand 0.4.0 实机）**

- 预置 `[[paired]]` 生效：必须是**顶层**数组表（`[host.paired]` 不被读取，被控端日志仍是 `paired=0`），写入后 `paired=1`、`admission=Known`。已预置公钥的控制端用 Noise XX 完成首次握手。
- Go 侧的握手与密钥派生与被控端字节一致：三次会话的安全码在路由器 `ready` 与被控端日志里完全相同（`497-256`、`225-902`、`305-843`）。
- CBOR 编码兼容：真实被控端的 `Register` 被解析，`HostMsg::Hello`（主机名/系统/版本/显示器/编码器列表）被我们的实现逐字段解出；上行 `ControllerMsg::Audio{enabled:true}` 触发被控端 `audio capture started`；数据报 `Ping` 得到 `Pong`。
- 首次会话走 XX 并学到被控端公钥（`hosts.perf_key`），第二次起走 IK，被控端同样接受。

**待验证（M8）**

- 浏览器用 WebCrypto 能否解开被控端发来的控制帧和视频包，计数起点和窗口规则是否与源码一致。
- 流内帧长度前缀的格式；`Ack`、`Lost`、`Report` 的最小必要集；被控端对缺失消息的容忍度。
- 空闲桌面长时间不动的保活表现，以及被控端托盘「更换控制码」后配对清空的重置流程。

### 4.10 路由器 perfgw 设计（本项目要写的代码之一）

`internal/perfgw/` 是 deskgw 内的一个 Go 包。它不解密、不解析视频和控制消息，只负责：被控端接入、握手、会话密钥下发、密文转发与背压。

| 文件 | 职责 |
| --- | --- |
| `quic.go` | QUIC 服务端、自签证书与指纹、连接接受、来源限流 |
| `signal.go` | 信令四条消息的编解码与处理 |
| `registry.go` | 在线被控端表（主机 id → 连接）、待批准列表、重连密钥校验 |
| `handshake.go` | Noise XX / IK 握手、Split、HKDF 派生各通道密钥、`Confirm`、解开被控端的决定 |
| `keys.go` | 组装会话密钥包（4.9），握手结束、ready 发出后立即清零路由器内存里的会话密钥 |
| `relay.go` | 被控端流与数据报 ↔ 浏览器 WebSocket 的密文转发、会话号校验、背压与丢帧 |
| `console.go` | 浏览器 WebSocket：票据、`connect` / `ready` / 错误 / 心跳 |
| `limits.go` | 会话名额（全局、每主机）与上行限速 |
| `ticket.go` | 一次性连接票据（30 秒、绑定用户与来源 IP） |

握手阶段需要的 CBOR 只有信令、`HandshakeInit`、握手回复和被控端决定这几种，属于小子集；握手之后的消息路由器一概不解析。

**与浏览器的转发协议（自定义，位于同一条 WebSocket）**

- 文本（JSON）：浏览器发 `connect`（主机占位符 `h<主机id>`）、`disconnect`、`ping`；路由器回 `ready`（会话密钥包、主机名称与系统、安全码）、`error`（错误类型）、`ended`（原因）、`pong`。初始画质与窗口尺寸不放在握手里：握手使用固定的默认值，浏览器在 `ready` 之后用 `Settings`、`View` 消息设置。
- 二进制，首字节是类型：
  - `0x01` 下行流数据：`0x01 | 通道号 u8 | 流序号 u32 小端 | 标志 u8 | 数据块`。路由器给被控端打开的每条单向流编一个流序号；标志位 0 表示该流已结束，标志位 1 表示整帧被路由器丢弃。
  - `0x02` 下行数据报：`0x02 | 种类 u8 | 密封单元`。
  - `0x11` 上行流数据：`0x11 | 通道号 u8 | 数据块`，写入路由器为该通道开的常驻单向流（只允许控制通道）。
  - `0x12` 上行数据报：`0x12 | 种类 u8 | 密封单元`（只允许控制数据报，不超过 1000 字节）。
- 路由器在上行数据前自己补上会话头（会话号和通道号），浏览器无法指定会话号，也就无法发送属于其他会话的数据。

**背压与丢帧**

- 每个会话有一个向浏览器的写队列（暂定 32MiB、1024 条）。
- 视频：队列超限时，新到的视频帧流直接丢弃（取消读取），已经转发了一部分的帧发出"整帧丢弃"标志；浏览器靠媒体包序号发现缺口，发送 `Lost` 请求关键帧，不断开。
- 控制通道不丢包，超限即断开会话；视频持续超限超过 10 秒也断开。
- QUIC 的流与连接接收窗口要大于一帧的上限，具体数值在 M7 实测。
- 路由器对上行有大小限制：单条消息不超过 64KiB，数据报不超过 1000 字节，并限制每秒条数，防止被滥用。
- 被控端在局域网里不可信（可被冒充），所以信令、握手回复、流头的解析都要限制长度并做模糊测试。
- 加解密负担：路由器只有 QUIC 解密和 WSS 加密两次，没有端到端解密，也不解析视频。amd64 与 arm64 通常有硬件加速，MIPS、armv7 不建议开启性能模式。

**限额**

- `perf.max_per_host`（默认 1）、`perf.max_sessions`（全局，默认 2）、每用户并发上限（沿用 `users.max_sessions`，在签发票据时检查）。
- 名额在握手成功后占用，在会话结束、控制台连接关闭时释放；连接关闭时按会话表一次性释放，防止泄漏。
- 强制下线：关闭浏览器侧连接，并关闭给该会话开的流；被控端因收不到心跳而按失联结束会话，超时时间以源码为准。

**错误处理**

| 场景 | `error.kind` | 处理 |
| --- | --- | --- |
| 主机不在线、未批准、用户无授权 | `codeNotFound` | 统一回复，不暴露主机是否存在 |
| 这台主机已有会话 | `hostBusy` | 提示先结束那一个 |
| 全局名额已满 | `limit` | 提示稍后再试或调高限额；与 `hostBusy` 分开，避免用户去结束自己的会话 |
| 被控端拒绝（控制端公钥未预置） | `pairingRequired` | 用户侧显示"该主机的性能模式尚未配置"；后台标红 |
| 被控端公钥变化 | `hostKeyChanged` | 阻断；后台提示管理员核对安全码后重新批准 |
| 握手失败、协议版本不一致 | `incompatible` | 提示被控端与服务端版本不一致 |
| 拨号超时、链路中断等临时故障 | `serverError` | 提示稍后重试并查看网关日志；不再误报成版本问题 |

错误类型沿用 Airhand 控制台已有的名称，浏览器控制端把它们映射成界面里已有的文案。

**审计事件**

`perf.host_register`（新被控端出现在待批准列表）、`perf.approve`、`perf.connect`（用户、主机、来源 IP）、`perf.connect_failed`（错误类型）、`perf.end`（时长、原因）、`perf.kick`。性能模式下看不到会话内的操作，审计只记录连接层面。

**配置项**

UCI：`perf_enabled`、`perf_listen`（默认 `0.0.0.0:4433`，建议绑定 LAN 接口）、`perf_cert`、`perf_key`、`perf_identity`（控制端的 X25519 私钥，权限 600，必须备份，丢失后所有被控端要重新预置配对）。后台设置：`perf.max_sessions`、`perf.max_per_host`、`perf.ticket_ttl`（默认 30 秒）、注册限流。

**测试**

- 协议样本：用真实被控端抓取的信令、握手和会话开头的字节做 fixture，覆盖握手与密钥派生，密钥包交给 4.11 的浏览器端测试复用。
- 兼容性测试：Windows 虚拟机里的被控端连测试用 deskgw，验证注册、批准、握手、出画面、断开；被控端每次升级都跑一遍。
- 模糊测试：信令、握手回复、流头解析。
- 压力测试：模拟 30Mbps 视频流，观察路由器 CPU、内存、背压与丢帧行为。

### 4.11 浏览器控制端（本项目要写的代码之二）

浏览器控制端用 TypeScript 写，运行在 Web Worker 里，负责握手之后的全部会话逻辑：解密、帧与消息处理、确认与丢帧恢复。路由器减下来的负担，就是由它接手的。

| 模块 | 职责 |
| --- | --- |
| `client.ts` | 与路由器的 WSS：票据、JSON 消息、二进制转发协议（4.10）、心跳；连接断开即会话结束，不做会话级重连。`ready` 之后才把密钥交给 Worker |
| `wire.ts` | 导入会话密钥（WebCrypto `importKey`，AES-GCM）；密封单元的解封与封包（12 字节 nonce，计数在末尾）；媒体包头与 SPS → codec 字符串 |
| `cbor.ts` | 用到的消息的 CBOR 子集（带编号字段）：被控端消息、控制端消息、数据报 |
| `messages.ts` | `HostMsg` 解析；`RequestKeyframe`、`Ack`、`Ping`、`Echo` 的编码 |
| `worker.ts` | 按流序号重组下行数据块、控制通道顺序解密、WebCodecs 解码、`Ack` 与关键帧请求 |
| `web/src/views/PerfView.vue` | 界面：画布、安全码、状态栏（分辨率、帧率、码率、RTT）、错误提示 |

键鼠已接并实测：鼠标归一化坐标、光标三态（`shown`／`inFrame`／`hidden`）、`ReleaseAll`；键盘分「文本 / 物理键」两模式（面板里切、localStorage 记住）：文本模式下可打印字符经隐藏 `textarea` 走 `Text`，输入法组字、emoji 都能上屏；物理键模式下所有键走 `Key`，中文不发送，给读扫描码的程序用。剪贴板双向已接（大块通道，只传文本：下行自动写本地剪贴板，上行在 `paste` 里推送并补一对 `KeyV`，由被控端自己粘贴）。输入方式可在「指针 / 触摸」间切换：触摸走 `InputEvent::Touch`（多点、四阶段），只在 `HostHello.touch` 为真时可选；手机点画面不弹软键盘。触屏的「指针」模式与普通模式共用同一套触控板交互（相对位移 + 自绘光标 + 单击/双击拖拽/长按右键/双指滚动），鼠标路径不受影响。会话页顶栏已取消，主机信息、读数与操作都收进可拖动的悬浮面板（与普通模式一致，位置单独持久化）。画质设置与 `Report` 还没接，`Lost` 用 `RequestKeyframe` 代替（每帧一条流，缺帧由本端判断）。已知限制：系统级 ANSI 对话框（Win+R）收不到 Unicode 文本；光标形状（`CursorImage`）受网关丢弃的限制，暂时只有一个箭头；剪贴板不传图片与文件；Windows 被控端不支持触摸注入，手机上只能用带触控板手势的指针模式。

**解密与性能**

- 用 `crypto.subtle.decrypt` 做 AES-256-GCM，由浏览器调用 CPU 的硬件指令；在 Worker 里处理，解密结果用可转移的 `ArrayBuffer` 交给解码，避免拷贝。
- 每个密封单元一次异步调用；高码率下的调用开销需要在 M7 实测，必要时对同一帧内的多个包并行解密。
- 浏览器要求：支持 WebCrypto、WebCodecs 和 Worker 的现代浏览器（Chrome、Edge、Safari 16.4+、Firefox 130+），页面必须是 HTTPS。

**确认与丢帧恢复**

- 一帧的所有包解密并组齐后，发一个 `Ack` 数据报；周期性发送 `Report` 以便被控端调整码率（建议实现）。
- 序号出现缺口或超时未补齐：发 `Lost`，仍无法恢复则发 `RequestKeyframe`。
- 收到路由器的"整帧丢弃"标志时，立即释放该流的组装状态，缺口由上面的规则处理。
- 失联检测：一段时间收不到 `Pong` 或任何数据就结束会话，超时值以源码为准。

**安全**

- 会话密钥只存在于 Worker 内存，不写入 localStorage、IndexedDB 或日志，会话结束后清零。
- 顺序规则和滑动窗口必须与被控端一致，否则表现为丢包或解密失败。
- Worker 脚本与页面同源，由路由器提供，路由器仍在信任边界内；端到端加密的收益在性能，不在抵御恶意路由器。

**测试**

- 用 4.10 的协议样本，在 Node 里借助 WebCrypto 测试解密、帧解析、CBOR 子集的编码解码往返。
- 在 Chrome、Edge、Safari、Firefox 上实测解密吞吐与 Worker 的 CPU 占用。
- 回放 30Mbps 以上的录制流，测端到端延迟。

- 批量部署：静默安装参数没有核实，需在 M7 确认。

## 5. 数据模型（SQLite）

```
users(id, username UNIQUE, pass_hash, role, enabled,
      allow_file, allow_clipboard, max_sessions, totp_secret, created_at)

hosts(id, name, address, rdp_port, smb_port, group_name,
      note, enabled, created_at)

user_hosts(user_id, host_id)            -- 授权关系，联合主键

sessions(id, user_id, host_id, client_ip, started_at, ended_at, state, mode)

audit_logs(id, ts, user_id, action, target, detail, client_ip)

settings(key PRIMARY KEY, value)        -- 超时、限流、文件限制等
```

`users.totp_secret` 是预留字段，当前没有实现双因素登录，只有 `has_totp` 一个只读标记；`users.max_sessions` 是每用户并发上限，默认 2、硬上限 32，前端标签数取自 `/api/me` 下发的值，不再自己写死。

**性能模式新增字段**

```
hosts     新增 modes TEXT DEFAULT 'rdp'        -- 'rdp'、'perf' 或 'rdp,perf'
          新增 perf_key BLOB                   -- 被控端公钥（首次握手时记录）
          新增 perf_secret BLOB                -- 重连密钥的校验值
          新增 perf_name TEXT, perf_os TEXT    -- 被控端报告的名称与系统
          新增 perf_last_seen INTEGER          -- 最近一次在线时间
sessions  新增 mode TEXT                       -- 'rdp' 或 'perf'
settings  新增键 perf.enabled、perf.max_per_host（默认 1，上限 8）、perf.max_sessions（默认 2，上限 32）
```

「待批准的被控端」不落库：它本来就是内存里的在线连接，进程重启后必须重新注册，落库只会留下清理不掉的过期记录；后台从 `perfgw` 注册表读待批准列表，批准时新建或关联一条 `hosts` 记录，并把控制码换成主机 id。

主机 id 同时作为分配给被控端的控制码，所以 `hosts.id` 必须在 u32 范围内。

数据库文件默认存放在 `/etc/deskgw/data.db`（`data_dir` 可改，需落在持久化分区）；注意这只解决数据库本身，审计和会话记录长期增长仍会写 overlay，Flash 磨损敏感时把 `data_dir` 指到 `/mnt/usb` 或外置存储。

## 7. 安全设计

1. **传输安全**：仅监听 HTTPS；首次启动生成自签证书与密钥，路径由 UCI 指定，可自行放入正式证书替换后重启；HTTP 跳转监听需显式配置 `redirect_listen`（默认关闭），失败时只记警告、不影响主服务。
2. **凭据不落地**：Windows 密码默认只存在浏览器内存，经 NLA 直接与 Windows 协商；文件通道凭据仅驻留内存、随会话销毁。
3. **反 SSRF**：隧道目标只能来自数据库，且限制为私网地址；唯一的例外是「仅性能模式」的主机——QUIC 由被控端主动接入，网关不外连，因此允许公网地址。票据一次性、30 秒过期、绑定用户与 IP。
4. **访问控制**：每次建立隧道与文件操作都重新校验用户-主机授权；管理接口强制 admin。停用用户、撤销主机授权、关闭主机时会断开其在线隧道（按「同一用户 + 同一主机」匹配，不会误踢同一主机上的其他用户）。
5. **防暴力破解**：登录与票据接口限流，失败计数 15 分钟窗口、5 次锁 10 分钟；管理员可查看异常。
6. **公网暴露建议**：强烈建议**不要把服务直接暴露公网**，优先通过 WireGuard/OpenVPN 接入；若必须暴露，需修改默认端口、配合 fail2ban 与防火墙来源 IP 限制（TOTP 尚未实现，不能作为依赖）。
7. **Windows 侧建议**：启用 NLA，使用强密码，禁用空密码登录，限制可远程登录的用户组。
8. **安全头与 XSS**：严格 CSP、`X-Frame-Options: DENY`、输出转义；上传文件名做路径穿越检查（拒绝 `..`）。

**性能模式补充**

- 网关授权是外层防线：被控端以 SYSTEM 运行，连上即管理员权限，所以每次签发票据和每条 `connect` 都校验"用户 - 主机"授权。
- 被控端接入口只监听局域网接口；未批准的被控端不转发任何用户数据，注册限流；批准时核对安全码；被控端公钥变化即阻断。
- 来自被控端的所有数据都按不可信处理：每个解析入口限制长度，并做模糊测试。
- 控制端密钥（`perf_identity`，权限 600）纳入备份，丢失后所有被控端要重新预置配对。
- 路由器只握手并转发密文，不解密画面；但会话密钥经 WSS 交给浏览器，页面脚本也由路由器提供，所以路由器仍在信任边界内。长期身份密钥只留在路由器，不下发给浏览器。
- 每台主机默认只允许 1 个性能会话，避免多人同屏操作互相干扰；强制下线沿用后台会话管理。
- 被控机设置无操作自动锁屏，让 Windows 登录界面成为第二道防线。

## 8. OpenWrt 部署设计

- **打包**：提供 `deskgw_<ver>_<arch>.ipk`（24.10）与 `deskgw-<ver>_r1_<arch>.apk`（25.12 / snapshot），含 LuCI 配置页 `luci-app-deskgw`；CI 实际交叉编译 `x86_64` 与 `aarch64_cortex-a53`（an7581）两种架构，其它架构可在 ImmortalWrt SDK 中自行编译。
- **服务管理**：`/etc/init.d/deskgw` 使用 procd，崩溃自动拉起，日志走 `logd`（`logread -e deskgw`）。
- **配置**（UCI，`/etc/config/deskgw`）：

```
config deskgw 'main'
    option enabled '1'
    option listen '0.0.0.0:8443'
    option cert '/etc/deskgw/server.crt'
    option key  '/etc/deskgw/server.key'
    option data_dir '/etc/deskgw'
    option session_idle_min '30'
    option max_upload_mb '2048'
    option redirect_listen ''
    option gomemlimit ''
    option perf_enabled '0'
    option perf_listen '0.0.0.0:4433'
```

- **端口**：默认 8443，避免与 LuCI（uhttpd 80/443）冲突；防火墙默认仅放行 LAN 区域，公网访问需用户手动开放。
- **存储与资源**：二进制建议使用 UPX 压缩；设备 Flash 不足时可安装到 USB（extroot）。最低建议：128MB 内存、16MB Flash（压缩后）。`data_dir` 在 overlay 上，审计与会话记录持续写入会带来闪存磨损，长期运行建议把 `data_dir` 指到外置存储。
- **升级**：`opkg upgrade` 保留 `/etc/config/deskgw` 与数据库；数据库带 schema 版本号，启动时自动迁移。`session_idle_min`、`max_upload_mb` 只在数据库尚无对应设置时作为初始值写入，之后以管理后台为准。
- **LuCI 集成**：提供启停开关、监听端口、证书名称，基本设置末尾另有内存软上限与 HTTP 跳转监听两项高级参数，并一键跳转到管理后台；性能模式单独分区，含启用开关、QUIC 监听地址（建议绑 LAN），以及证书、私钥、控制端身份私钥三条只读路径与备份警告。改完需重启服务。被控端对接参数（`server`、`server_fp`、`[[paired]].key`）是运行时派生值，只在管理后台「性能模式」页展示，不放 LuCI。管理后台的状态页显示版本、运行时长、在线会话数、主机与用户数、性能模式状态。

**性能模式部署补充**

- 不新增进程：perfgw 随 deskgw 启动，多监听一个 UDP 端口（默认 4433），防火墙只对 LAN 区域放行。
- 证书：首次启动自动生成自签证书和密钥（`perf_cert`、`perf_key`），后台显示证书指纹，供构建被控端安装包使用。
- 控制端密钥：首次启动生成 X25519 密钥（`perf_identity`，权限 600），后台显示公钥，供预置被控端的 `[[paired]]`。
- 内核 UDP 缓冲：LuCI「性能模式」分区提供开关（默认开启）与缓冲上限（默认 8MiB，可改）。服务启动时由 `/usr/libexec/deskgw/udp-tune.sh` 写入 `net.core.rmem_max` / `wmem_max` 并持久化到 `/etc/sysctl.conf`，用标记块管理、重复调用会覆盖旧值；关闭时移除该块。不设的话高码率视频会因缓冲被填满而卡顿。
- UCI 增加 `perf_*` 选项（见 4.10）。
- 构建：仍是 Go 单一二进制，QUIC 使用 quic-go，不需要 Rust 和 Docker；性能模式只建议用于 amd64 和 arm64 设备。

## 9. 性能与容量估算

- 网关 CPU 开销主要来自 TLS 加解密与字节拷贝；在 MT7621（双核 880MHz）上，预计可稳定支撑 **3–5 路并发 1080p 会话**；x86/aarch64 设备可支撑 20 路以上。
- 画面编解码在浏览器完成，路由器不受分辨率与色深影响。
- 文件传输为流式，单路吞吐受限于路由器 CPU 的 TLS/SMB 性能，千兆 ARM 设备约 30–80MB/s。
- 提供后台"最大并发会话数"全局限制，防止路由器被压垮。

**性能模式负载**

- 每路会话在路由器上只有 QUIC 层解密和到浏览器的 TLS 加密两次处理，不做端到端解密，也不解析视频。1080p60 约 20–50Mbps 一路，吞吐是估计值，需要实测。
- 解密移到浏览器：WebCrypto 的 AES-256-GCM 有硬件加速，在 Worker 里处理，浏览器端的 CPU 占用需要在 M7 实测。
- 没有中继和网页控制台，少了一跳转发和两个额外进程的内存。
- amd64 与 arm64 设备预期可行；MIPS、armv7 没有硬件加密加速，不建议开启。
- 后台增加全局 `perf.max_sessions`（默认 2），防止路由器被压垮。

| IronRDP 对部分 Windows 版本/策略兼容性不足 | 无法连接或画面异常 | M2 即做兼容性矩阵测试；保留方案 A（guacd）作为可切换的后备中继 |
| 路由器性能过低 | 并发体验差 | 限制并发数；文档给出机型建议 |
| 家庭版 Windows 不支持 RDP 服务端 | 部分主机不可用 | 文档说明，主机添加时探测并提示 |
| 公网暴露带来攻击面 | 被爆破/入侵 | 默认仅 LAN；推荐 VPN；强制 TOTP 与限流 |
| SMB 445 被 Windows 防火墙/策略禁用 | 文件功能不可用 | 提供检测与一键配置脚本；功能降级为仅 RDP |
| 内置 WASM 体积较大 | 首次加载慢 | 开启 gzip/brotli、浏览器长缓存 |
| 性能模式在路由器上转发高码率视频 | 弱 CPU 设备卡顿 | M7 实测；全局限制并发；MIPS、armv7 不开启 |
| 被控端升级后协议版本变化 | 握手失败，或浏览器控制端无法解密 | 锁定被控端版本并自行构建安装包；升级前先跑协议兼容测试，再同步升级 perfgw 与浏览器控制端 |
| 自研握手、密钥派生与消息编码与被控端不兼容 | 连不上，或会话中途异常 | M7 先用真实被控端验证；失败则回退到复用 airhand-link 的 Rust 方案 |
| 预置配对（\[\[paired\]\]）未验证 | 被控机仍需现场配对 | M7 验证；不可行则第二期实现 SPAKE2 配对 |
| 局域网内设备冒充被控端 | 伪造注册、投送恶意数据 | 未批准不转发数据；批准时核对安全码；注册限流；解析入口限制长度并做模糊测试 |
| 被控端以 SYSTEM 运行，授权被绕过即管理员权限 | 严重 | 网关校验票据与每次连接的主机授权；被控机自动锁屏 |
| 同一主机多人同屏 | 操作互相干扰 | 默认每台主机 1 个性能会话 |
| 摘用的前端与上游控制台分叉 | 维护成本上升 | 只摘用必要部分，锁定上游版本 |
| 浏览器端解密性能不足（低端设备、各浏览器差异） | 画面卡顿、丢帧 | M7 在各浏览器实测；Worker 内解密、并行处理；提供帧率和码率上限 |
| 会话密钥经 WSS 交给浏览器 | 浏览器侧泄露会暴露该会话 | 仅存在内存、会话结束清零、不写日志；长期密钥不下发 |

## 13. 后续规划
